# Personalized Learning Path — How It Works

## From the student's perspective

When a student opens a course they're enrolled in, a **"Your Path"** card appears at the top of the sidebar, above the regular lesson list.

**First visit:** The card shows a "Get your personalised path" button. Nothing is generated automatically — the student initiates it.

**After generating:** The card shows 3–5 ordered next steps. Each step is one of three types:
- **New** — a lesson the student hasn't touched yet
- **Review** — a lesson they completed, but a concept from it is weak
- **Retry quiz** — a quiz they answered incorrectly

Each step has a one-sentence reason grounded in their actual data ("You scored 0/1 on the Arrays quiz" or "Your mastery of recursion is 1/5"). Clicking any step navigates directly to that lesson — retry-quiz steps deep-link to the quiz within the lesson.

Below the steps, small chips list the weak concepts the path is addressing.

**Stale state:** When the student completes a lesson or submits a quiz answer, the path is silently marked as outdated. On their next visit a yellow banner appears: "Your path may be outdated — regenerate to update." The old steps remain visible until they click **Regenerate**.

**Regenerate:** Clicking the button streams live progress ("Analyzing your progress…", "Writing reasoning…") while the path is being rebuilt. The card updates in place when done. Rate-limited to once per minute per course.

---

## What data drives it

The path is built from signals already collected by the platform:

| Signal | Source | Meaning |
|---|---|---|
| Completed lessons | `LessonProgress` | What the student has already done |
| Quiz attempts | `QuizAttempt` | Whether they got each quiz right or wrong |
| Concept mastery | `ConceptMastery` | 0–5 score per concept, updated by the lesson AI assistant |
| Lesson concepts | `LessonInsights` | Which concepts each lesson covers (generated by the AI insights feature) |

## How the system builds the path

The generation runs as a **LangGraph `StateGraph`** — a graph of nodes where most steps are plain code and only two steps call the LLM. This is intentional: filtering completed lessons and identifying weak concepts is deterministic logic that doesn't need a model.

### The graph, step by step

```
loadStudentSignal
      │
identifyWeakSignals
      │
  decideStrategy ──────────────────────┐
  (conditional edge)                   │
      │ has weak signals?         empty (no activity yet)?
      ▼                                ▼
proposeReviews          setSkipLLM → proposeNewLessons
      │                                │
      └────────────────────────────────┘
                         │
               proposeNewLessons
                         │
               mergeAndExplain  ◄──── (retry if reflection fails)
                         │
               reflectAndCheck
                         │
                      persist
```

**Node 1 — `loadStudentSignal`**
Five parallel Prisma queries: enrollment check (also verifies course is published), lesson order, quiz attempts, concept mastery, completed lessons. Throws `CourseUnavailableError` if the student isn't enrolled or the course is unpublished.

**Node 2 — `identifyWeakSignals`**
Pure filtering. Concepts with mastery `< 3` become `weakConcepts`. Quiz attempts that were wrong become `failedQuizzes`, deduplicated by lesson.

**Node 3 — `decideStrategy` (conditional edge)**
No LLM. Branches:
- `empty` → student has zero completed lessons and zero quiz attempts → `skipLLM = true`, go straight to first 3 lessons
- `hasWeak` → there are weak concepts or failed quizzes → propose reviews first
- `ready` → all quizzes correct, all studied concepts strong → skip reviews, propose new lessons only

**Node 4 — `proposeReviews`** (only on `hasWeak`)
Picks up to 3 lessons to review (one per weak concept) and up to 2 quizzes to retry. These are `DraftStep` objects with a mechanical reason seed ("Mastery of 'closures' is 1/5").

**Node 5 — `proposeNewLessons`**
Appends up to 3 next uncompleted lessons in curriculum order. Always runs.

**Node 6 — `mergeAndExplain`** (LLM: `gpt-4o-mini`, temp 0.3)
Receives all candidate steps. Before calling the model, fetches lesson summaries and quiz attempt history for each candidate (from `LessonInsights`). The model picks the best 3–5 steps and writes a concrete one-sentence reason for each.

The output goes through a **semantic validator** before being accepted. The validator checks:
- Every `lessonId` belongs to this course
- `NEW_LESSON` steps reference lessons the student hasn't completed
- `REVIEW_LESSON` steps reference lessons the student *has* completed
- `RETRY_QUIZ` steps reference a quiz the student actually failed

If the model hallucinates a bad step, the violation is fed back as a correction prompt. Up to 3 attempts; if all fail, a `LearningPathInvalidError` is thrown.

On the `skipLLM` path (zero-activity students), the node returns the first 3 lessons with canned reasoning — no model call, no tokens spent.

**Node 7 — `reflectAndCheck`** (LLM: `gpt-4o-mini`, temp 0)
A second, cheaper model call reviews the proposed steps. It checks whether the balance between review/new steps is reasonable, weak concepts are addressed, and steps are not repeated. If it flags issues, feedback is passed back to `mergeAndExplain` for one retry. After 2 reflection attempts the path is accepted as-is.

### Persistence and cache invalidation

One `LearningPathCache` row per (student, course). Each regeneration overwrites it. The row stores:
- `steps` — the final step list as JSON
- `summary` — the overall summary sentence
- `weakConcepts` — concept name chips for display
- `generatedAt` — timestamp shown in the UI
- `staleAt` — set to `now()` by fire-and-forget hooks when the student submits a quiz or changes a lesson's completion state

The hooks are fire-and-forget: if the `markStale` write fails, it logs a warning and the student just sees the stale banner for a bit longer. It doesn't affect the quiz/lesson operation itself.

### API surface

| Endpoint | Type | Purpose |
|---|---|---|
| `api.learningPath.getForCourse` | tRPC query (`studentProcedure`) | Read the cache row on every course page load. Cheap. |
| `api.learningPath.regenerate` | tRPC mutation (`studentProcedure`) | Trigger regeneration; returns the persisted result. |
| `POST /api/chat/learning-path` | SSE route | Same regeneration, streamed. The UI uses this for live progress updates. |

The SSE route and the tRPC mutation share the same service method (`streamRegenerate` vs `regenerate`). The rate limiter (in-process `Map`, 1 call/60s per student+course key) is checked in both paths.
