# Learnix Documentation & Development Process

**Status:** Decision
**Date:** 2026-06-23
**Scope:** how features get designed, specced, built, and documented in this repo from now on.

---

## 1. The model in one paragraph

Source of truth splits three ways — full rationale and alternatives considered are in
**[ADR-020](../adr/020-hybrid-documentation-model.md)**; this document is the operational mechanics
that ADR deliberately leaves out.

```
Intent      → spec.md          (why / what, business framing)
Decisions   → docs/adr/         (why this way, not another way)
Correctness → tests/evals/CI    (does it actually work, right now)
```

Each artifact stays thin and pointed at the one thing only it is good at: a passing test suite
doesn't tell you *why* a feature exists, and a spec doesn't guarantee the code matches it.

## 2. Directory structure

```
docs/
  adr/                                   ← unchanged, already in use (ADR-001..019)
  specs/
    _legacy/                             ← the 36 existing dated folders, moved here verbatim
      2026-05-04-auth/
      2026-05-04-course-management/
      ... (30 more)
    mission.md, tech-stack.md, roadmap.md   ← unchanged
    documentation-process.md              ← this file, the live decision
    features/
      _index.md                          ← GENERATED by `pnpm spec:sync` — never hand-edited
      <slug>/
        spec.md                          ← the one living doc per feature
        build/
          plan.md                        ← detailed implementation plan (standard + complex)
docs/templates/
  feature-spec.md                        ← template for spec.md
  plan.md                                ← template for build/plan.md
```

Only two documents are used per feature: `spec.md` (the living design) and `build/plan.md` (the
detailed implementation plan, produced with `writing-plans`). The earlier 4-document flow
(`requirements.md → spec.md → plan.md → validation.md`) is retired — fold problem/scope into
`spec.md`'s Purpose/Functional scope, and verification into the plan's per-task tests and its
`## Final verification` section.

Nothing in `_legacy/` is read by an agent unless a human explicitly points at it. Everything an agent
needs to navigate starts at `features/_index.md`.

## 3. Tiers — how much process a change gets

| Tier | Trigger | Artifacts | Real example |
|---|---|---|---|
| **trivial/fix** | no change to any feature's documented behavior — bug fix, refactor, internal correctness | none — TDD against harness only | fixing a race in `EnrollmentService.enrollInCourse`'s idempotency check |
| **standard** | adds or changes a feature's user-visible behavior (Functional Scope / Acceptance Criteria), built from existing patterns — *may include a new model or table* | `features/<slug>/spec.md` + `build/plan.md` | the messages feature (inbox/thread/composer) merged 2026-06-23 |
| **complex** | touches money, the auth/security model, a new external service, or a data migration that's risky/expensive to reverse on existing production data | same `spec.md` + `build/plan.md` as standard, **plus an ADR** | the Stripe Connect payments rework (→ ADR-019) |

The tier decides the *ceremony*, not the rigor of the harness — trivial-tier work still needs tests,
it just skips the design-doc round-trip because the harness already catches regressions in
well-covered zones (repositories, lib, core services).

### 3a. Deciding the tier

Run these three questions in order, stop at the first "yes":

1. **Does it touch money, the auth/security model, a new external service, or a data migration
   that's risky/expensive to undo on existing data?** → **complex**, full stop, regardless of how
   small the code diff looks. This is deliberately narrower than "any new schema" — a new Prisma
   model by itself (a join table, a simple new entity) does **not** trigger this on its own; see the
   wishlist example below.
2. **Does it add or change a line in some feature's Functional Scope or Acceptance Criteria** — i.e.
   would a user or instructor notice the behavior is new or different? → **standard**, even if it
   needs a new model/table to get there.
3. **Neither** — same documented behavior as before, just fixed, refactored, or made faster/safer
   internally → **trivial**.

**Why "new schema" alone isn't the complex trigger:** the wishlist example in §8 adds two new models
(`Wishlist`, `WishlistItem`) and is still standard tier — nothing about it is risky to reverse (drop
the tables, no data loss anyone cares about) or touches money/auth/an external service. Contrast with
the subscriptions example, where the schema change is risky precisely because it reshapes how money
already in flight (the existing `transferStatus: pending` sweep) gets reconciled — that's what earns
the complex tier and the ADR, not the row count of `prisma/schema/`.

### 3b. How a developer talks to the agent

The developer never declares a tier — they just describe the bug or the intent in plain language,
and the agent infers the tier from §3a once it knows what the change actually touches. What's worth
including in the prompt differs by kind:

**Bug report** — symptom + expected behavior is enough. No need to mention specs, ADRs, or tiers at
all.

```
Users can enroll twice in the same course if they double-click "Buy" — fix it.
```
```
The wishlist badge in the sidebar shows a stale count after removing an item from the list.
Refreshing the page fixes it, so it's probably not invalidating a cache somewhere.
```

The agent diagnoses (`systematic-debugging`), writes a failing test, fixes it. If the root cause turns
out to touch money/auth/migration risk, the tier escalates mid-task automatically — the developer
doesn't need to have predicted that.

**Standard feature** — give the intent plus explicit scope boundaries. This is the one case where
detail upfront actually saves a round-trip, because `brainstorming` will ask for it anyway if it's
missing.

```
Add a wishlist feature: students can bookmark courses from the browse page without buying.
One list per student, no sharing between students, no email notifications for now — just a
save/unsave button and a "My wishlist" page.
```
```
Add a "duplicate course" action for instructors — copies title, sections, lessons (not the
content of published reviews/enrollments) into a new draft course they can edit before
publishing.
```

**Complex feature** — give the intent plus whatever constraints, deadlines, or business reasons you
already know. Not required for tier detection (the agent will see "money" or "new external service"
on its own from §3a), but it materially changes the design.

```
We want monthly subscriptions in addition to one-time course purchases. Needs to plug into the
existing Stripe Connect payout flow — don't want a separate ledger. Let's do this properly with
a spec and ADR before touching code.
```
```
Add an "organizations" concept: a company can buy N seats and assign them to employees. This
touches auth (org-scoped roles), payments (one invoice/many seats), and enrollment. Flag
anywhere this could become a bigger architectural fork.
```

**Overriding the inferred tier** — always possible, in either direction:

```
Quick fix, skip the spec — just patch it.
```
```
Even though this looks small, I want a proper spec for this one — it's going to be referenced
by three other features later.
```

## 4. `spec.md` format

```yaml
---
feature: messages
status: planned | in-progress | in-review | stable | deprecated
models: [Message, Conversation]    # optional
depends-on: [auth]                 # optional
---
```

**Status note:** `done` is replaced with `stable`. Almost nothing in this codebase is ever truly
finished — `courseAI` alone has had five follow-on PRs after its initial ship. `stable` means
"shipped, currently correct, not mid-change" without implying "will never be touched again." It's
still read-only by convention; a human flips it back to `in-progress` to reopen it — see Example 5
below for it in action.

Sections, in order:
- **Purpose** — why the feature exists, in business terms.
- **Functional scope** — what it does *right now*. No "previously / now" diffing — that's what git
  history is for.
- **Acceptance criteria** — the DoD. For AI features, phrase each one so it could become an eval case
  directly (mirrors the `evals/` pyramid in `CLAUDE.md`).
- **Agent notes** — anything an agent needs that isn't visible from reading the code (e.g. "tool_router
  routes are order-sensitive," "confidence_score ≥0.8 auto-advances").

## 5. ADRs

Unchanged from current practice, formalized: write one when, three months from now, someone asking
"why X and not Y" would need a real answer (the *3-month test*). Routine implementation choices don't
qualify. Existing ADR-001..019 are the bar — `019-payments.md` (merchant-of-record + Connect transfers)
is the canonical example of a decision worth the ceremony.

## 6. `_index.md` generation

`scripts/spec-sync.ts` scans `docs/specs/features/*/spec.md`, parses the YAML frontmatter, and
regenerates the table between `<!-- AUTO-GENERATED:START -->` / `<!-- AUTO-GENERATED:END -->`
markers. Runs via `pnpm spec:sync` and in the pre-commit hook (re-staging `_index.md` so it can
never lag behind a commit).

```
<!-- AUTO-GENERATED:START (run `pnpm spec:sync` — do not edit) -->
| Feature  | Status      | Depends on |
|----------|-------------|------------|
| auth     | stable      | —          |
| payments | stable      | auth       |
| messages | stable      | auth       |
| courseAI | in-progress | auth       |
<!-- AUTO-GENERATED:END -->
```

Honest caveat: this guarantees the index matches *frontmatter*, not reality. If you forget to bump
`status:` when shipping, the index will confidently lie. That's why "update frontmatter" is folded
into Gate Docs below, not left as a someday-chore.

## 7. Gate Docs — the DoD step

A PR doesn't close without:
1. `spec.md` updated (new feature → created; existing feature → frontmatter/sections refreshed).
2. `pnpm spec:sync` run, `_index.md` diff committed.
3. ADR written if the change crossed the 3-month-test bar.

This is the enforcement point for the "specs rot" problem — it's a checklist item on every PR, not a
separate audit pass.

## 8. Worked examples

### Example 1 — trivial tier: idempotency bug in enrollment

**Scenario:** `EnrollmentService.enrollInCourse` double-fires `recomputeUserInterest` under a race.

- No `spec.md` touched, no folder created.
- `systematic-debugging` skill to find the race, `test-driven-development` to write the failing
  integration test first, fix, green, ship.
- Gate Docs: nothing to update — the existing `enrollment` feature's `spec.md` (if one exists) didn't
  change in *what* the feature does, only in correctness. The harness now permanently enforces it.

### Example 2 — standard tier: course wishlist (hypothetical next feature)

**Scenario:** students can save courses to a wishlist from the browse page.

1. `brainstorming` skill to pin down scope (one list per student? shared? notify on price drop?).
2. Create `docs/specs/features/wishlist/spec.md` from `docs/templates/feature-spec.md`:
   ```yaml
   ---
   feature: wishlist
   status: planned
   models: [Wishlist, WishlistItem]
   depends-on: [course, auth]
   ---
   ## Purpose
   Students browsing courses they aren't ready to buy need a way to bookmark them instead of losing
   the course in their history.
   ## Functional scope
   - Add/remove a course to the caller's wishlist from the browse/course-detail page.
   - `wishlist.list` (studentProcedure) returns the caller's saved courses, newest first.
   - Wishlisted courses that get unpublished are silently dropped from the list.
   ## Acceptance criteria
   - Adding an already-wishlisted course is a no-op, not an error.
   - Wishlist count badge in the sidebar matches `wishlist.list` length.
   ## Agent notes
   - Mirrors the `Enrollment` repository pattern (BaseRepository), not a new abstraction.
   ```
3. Produce the detailed `build/plan.md` with `writing-plans` (from `docs/templates/plan.md`) and get
   it approved before writing code.
4. Implement with TDD against the harness (repository integration test, router test, component test).
5. Flip `status: planned → in-progress` while building, `→ stable` on merge.
6. Gate Docs: `pnpm spec:sync`, commit the regenerated `_index.md` row, no ADR (no schema risk, no
   external service, no money — doesn't clear the 3-month-test bar).

### Example 3 — complex tier: a hypothetical subscriptions model

**Scenario:** Learnix adds monthly subscriptions on top of the existing one-time Stripe Connect
purchases (real ADR-019 money flow already in the repo).

1. Write `features/subscriptions/spec.md` (new `Subscription` model, webhook handling for
   `invoice.paid`, interaction with the existing `transferStatus: pending` sweep logic — framed as
   Purpose / Functional scope / Acceptance criteria / Agent notes), then the detailed
   `build/plan.md` (TDD task breakdown via `writing-plans`), approved before code.
2. Because this touches money and an external service (Stripe) and changes the payout model,
   it clears the 3-month-test → write `docs/adr/020-subscriptions.md` explaining why recurring
   billing piggybacks on the existing Connect transfer flow instead of a separate ledger.
3. On ship: `spec.md` stays the living doc; freeze `build/plan.md` (kept, not deleted, not read by
   default), run `pnpm spec:sync`.
4. Gate Docs: spec + index + ADR, all three.

### Example 4 — cross-feature drift: adding an "organizations" concept

**Scenario:** a future `organizations` feature lets a company
buy seats across multiple students, which changes `auth` (org-scoped roles), `payments` (one invoice,
many seats), and `course` (org-wide enrollment).

- This is the case the Living Spec model *reduces but does not eliminate*. Three specs need updates:
  `features/auth/spec.md`, `features/payments/spec.md`, `features/course/spec.md` each get an added
  line — e.g. payments' Acceptance Criteria gains "a single checkout session can enroll N seats under
  one org-scoped payment."
- Gate Docs makes this enforceable, not automatic: the PR template / reviewer checklist should ask
  "did this change any *other* feature's documented scope?" before merge. No tooling catches a missed
  update here — this is the honest limit of the model, not a solved problem.
- If org-scoping turns out to be a genuine architectural fork (e.g. roles become org-relative
  everywhere), that's an ADR, not just three spec edits.

### Example 5 — reopening a "stable" feature: courseAI's revision flow

**Scenario** (this already happened in this repo): `courseAI` shipped, was marked `stable`, then later
gained the `revise_prior_field` node and `clarify` intent — a real behavioral addition, not a bugfix.

- A human flips `features/courseAI/spec.md` frontmatter `status: stable → in-progress`.
- Acceptance criteria gets a new line: "user can revise a previously-confirmed step without restarting
  the flow; `assess_completion` returns `ready: false` for revise turns."
- Agent notes gets the line that's currently load-bearing in `CLAUDE.md` itself: "Revision flow updates
  `content[reviseTarget]` via flat merge, persists immediately, emits `content_revised`."
- On merge: `status → stable` again, `pnpm spec:sync`. No ADR — this is a flow enhancement within the
  already-decided LangGraph architecture (ADR-016 already covers the *why* of the graph shape), not a
  new architectural decision.

## 9. What's deferred, not adopted

- **`features/` → `domains/` restructure** — genuinely useful at scale, premature now. Revisit when
  `features/` exceeds roughly 30–40 directories (it's currently backed by ~36 *legacy dated* folders
  being archived, and a fresh `features/` starting near zero). Don't build this speculatively.
- **AGENTS.md / slimming CLAUDE.md** — rejected: one rich `CLAUDE.md` costs fewer round-trips than a
  thin entry point plus a fatter doc tree for a project this complex.
- **CHANGELOG.md** — rejected; `git log` covers it for a solo-maintained repo.

## 10. Rollout checklist

1. `scripts/spec-sync.ts` — new, generates `_index.md` from frontmatter.
2. `package.json` — add `"spec:sync": "tsx scripts/spec-sync.ts"`.
3. `.husky/pre-commit` — run `pnpm spec:sync` after `pnpm check:write`, re-stage `_index.md`.
4. `docs/templates/feature-spec.md` — new template (Purpose/Functional scope/Acceptance
   criteria/Agent notes + frontmatter from §4).
5. `CLAUDE.md` — rewrite the *Development Workflow* section to point at this file's tiers, lifecycle,
   and Gate Docs steps; leave the rest of the file untouched.
6. Move the 36 dated folders: `docs/specs/<YYYY-MM-DD>-*/` → `docs/specs/_legacy/<same-name>/` (`git mv`,
   not delete).
7. Seed `docs/specs/features/_index.md` by running `spec:sync` once existing active features get their
   first `spec.md` (start with whatever's currently `in-progress`, backfill the rest opportunistically —
   don't block rollout on writing 36 specs upfront).
8. `docs/README.md` — update links to the new structure.

**Verification:** create a throwaway `features/sample/spec.md`, run `pnpm spec:sync`, confirm
`_index.md` adds/updates/removes the row correctly; `pnpm check` + `pnpm typecheck` clean; pre-commit
actually triggers `spec:sync`; `grep -r "docs/specs/2026-"` after the move finds no broken references.
